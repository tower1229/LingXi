# 调优检查清单

> **何时用本文**：需要一次性做全维度自查、或按项勾选并产出结构化调优报告时，用本清单。  
> **何时用指南**：需要按调度/执行/记忆/守护分层定位问题、或先定层级再调优时，用 `optimization-guide.md`。  
> 按层级视角与详细说明见 `optimization-guide.md`，本文保留作轻量速查与勾选用。

## 概述

基于核心价值指引（Why 和 How）与技术能力边界，提供可勾选的全维度调优清单；工程实践细则以 `engineering-practices.md` 为准，此处仅列要点提示。

## 价值对齐检查（基于 Why 和 How）

### 心有灵犀

- [ ] **是否有助于经验沉淀和复用？**（有助于记住创造者的指引）
- [ ] **是否有助于让 AI 按创造者的方式做事？**
- [ ] **是否有助于持久化记忆能力？**

### AI Native

与 `references/core-values.md` 中 AI Native 一致（尊重 AI 能力，预留进化空间；关键决策以人为主、门控保障）。以下为派生检查项。

- [ ] **是否尊重 AI 作为能力源泉？**
- [ ] **是否为 AI 进化预留空间？**
- [ ] **是否过度约束 AI？**（否 → 通过，是 → 需要调整）
- [ ] **是否把 AI 用在高语义/高歧义/需权衡环节？**
- [ ] **是否把高频、重复、可规则化步骤前置到确定性机制？**
- [ ] **高风险动作是否具备人工门控与降级路径？**

### 称心如意

- [ ] **是否降低认知负担？**
- [ ] **是否提供友好的交互体验？**
- [ ] **是否让常用操作更便捷？**

## 技术能力边界检查

### 组件选择

- [ ] **选择的组件是否符合其官方定义的适用场景？**
- [ ] **选择的组件是否在其能力边界内？**
- [ ] **是否有更适合的组件选择？**

### 性能考虑

- [ ] **性能开销是否可接受？**（基于官方定义的限制）
- [ ] **是否有性能瓶颈？**（否 → 通过，是 → 需要优化）

## 工程实践准则检查

调优时重点核对以下要点，**完整原则与检查点见 `engineering-practices.md`**（核心原则、设计模式、质量维度等）。

- [ ] **SSoT / SoC / DRY**：是否有重复定义或职责重叠？是否通过引用与分层共享信息？
- [ ] **KISS / YAGNI**：是否足够简单、在解决当前问题？是否存在过度设计？
- [ ] **Fail Fast / 显式优于隐式**：关键点是否验证、行为是否明确可读？
- [ ] **分层与约定**：层次与职责是否清晰？约定是否一致、配置是否最小化？
- [ ] **可观测与质量**：状态是否可见、决策是否可追溯？可维护性、可测试性、一致性是否满足？

## 调优建议输出

基于检查清单，输出：

1. **通过项**：哪些检查项已通过
2. **需要调整项**：哪些检查项需要调整，如何调整（参考 Why 和 How、工程实践准则）
3. **技术边界问题**：哪些超出技术能力边界，如何调整
4. **工程实践问题**：哪些不符合工程实践准则，如何改进
5. **权衡分析**：识别可能的权衡和取舍，根据项目阶段和实际需求做出合理决策
6. **风险评估**：哪些检查项存在风险，如何缓解
