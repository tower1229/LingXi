# Vet

## 意图

对 task 文档做多维度审查并输出改进建议；不产出文件，仅输出审查结果到对话。根据需求类型与复杂度从维度适配矩阵确定执行的维度（D1–D5），按各维度检查项执行并输出审查范围、总体评价、实施准备度、详细问题清单（仅有问题维度）、改进优先级。

## 关键约束

- **taskId**：指定则用该编号的 task；省略则执行 `node plugin/skills/task/scripts/latest-task-id.mjs` 获取最新任务编号。脚本失败则输出错误并终止。
- **元数据**：从 task 头部读取需求类型（前端/后端/全栈/简单功能/其他）、复杂度（简单/中等/复杂）、特性标签（可选：文档为主、库/SDK）。
- **维度**：简单功能仅 D1+D2；前端/后端/全栈按复杂度执行 D1–D4 或 D1–D5；D4 按类型或特性标签有不同分支。
- **下一步建议**：只要输出了审查结果（总体评价、问题清单或改进建议任一项），必须在当轮回复末尾输出「**下一步可尝试（选一项）**」+ 四项 A/B/C/D；允许集合：执行 plan skill、执行 build skill、调整 task、其他/跳过。

## 维度适配矩阵

| 需求类型 | 简单   | 中等                       | 复杂                       |
| -------- | ------ | -------------------------- | -------------------------- |
| 前端     | D1, D2 | D1-D4                      | D1-D5                      |
| 后端     | D1, D2 | D1-D5                      | D1-D5                      |
| 全栈     | D1, D2 | D1-D5                      | D1-D5                      |
| 简单功能 | D1, D2 | -                          | -                          |
| 其他     | D1, D2 | D1-D5（D4 按 D4 其他规则） | D1-D5（D4 按 D4 其他规则） |

## 维度定义

| 维度 | 名称       | 审查焦点                             |
| ---- | ---------- | ------------------------------------ |
| D1   | 需求完整性 | 目标、边界、用户故事、非目标是否清晰 |
| D2   | 可验证性   | 成功标准和验收标准是否可验证         |
| D3   | 方案合理性 | 技术选型和架构思路是否合理           |
| D4   | 规范完整性 | UI/API/数据模型等规范章节是否完整    |
| D5   | 风险识别   | 技术难点、外部依赖、风险是否识别     |

## D1–D5 检查项

### D1 需求完整性（通用必选）

- 检查：背景说明、问题描述、方案概述、目标是否清晰；中等及以上还需检查非目标与用户故事。
- 不检查：技术实现细节、代码结构设计（属于 plan/build）。

### D2 可验证性（通用必选）

- 检查：成功标准、验证方式、验收标准是否可验证；每条 F 是否有验证方式和可判定验收标准。
- manual/rubric 项必须有可执行验证步骤与预期结果（rubric 含评分维度）。
- 不检查：测试用例设计与自动化测试代码。

### D3 方案合理性（中等+）

- 检查：技术选型是否说明、架构思路是否清晰、选型理由是否充分；复杂需求可要求方案对比。
- 不检查：具体代码结构、性能调优细节、安全实现细节。

### D4 规范完整性（按类型触发）

- 前端：交互流程、界面状态、响应式要求（中等+）。
- 后端：API 路径、请求响应、错误码、数据模型、字段约束（按复杂度裁剪）。
- 文档为主：变更范围、受众/读者、版本或发布约定。
- 库/SDK：不执行前端 UI 规范；有对外接口时检查接口/行为约定。
- 其他：检查该任务形态下应有规范、变更范围、验收可执行性与对外交付方式。
- 执行顺序：文档为主/库SDK优先，其次其他类型分支，最后前后端分支。

### D5 风险识别（中等+）

- 检查：外部依赖、集成方式、技术难点、可行性结论；复杂需求需检查风险缓解思路。
- 不检查：降级实现、熔断限流配置、监控告警设计。

## 输出格式

审查范围（类型、复杂度、特性标签、维度） -> 总体评价（3-6 行） -> 实施准备度（含验证方式与验收覆盖判断） -> 详细问题清单（仅输出有问题维度） -> 改进优先级（Blockers/High/Medium/Low）。

## 下一步建议

只要输出了审查结果，回复末尾必须输出「**下一步可尝试（选一项）**」+ 四项 A/B/C/D。无 Blockers/High 时 A 推荐执行 plan 或 build skill；有 Blockers/High 时 A 推荐先改 task。允许集合：执行 plan skill、执行 build skill、调整 task、其他/跳过。

## 审查边界说明

task 定位是需求提纯与放大、核心技术方案/决策、可判定验收标准（不含实现细节）。不应审查代码级实现、详细性能安全实现、测试代码、部署运维配置。

## 使用场景

简单功能执行 D1+D2；复杂后端/全栈执行 D1-D5。

## 变更记录约定

当用户反馈导致对 task 文档的修改时，执行修改的 Agent 须在 task 文档的「变更记录」小节追加一条结构化记录。格式与位置见 task skill 的 `references/task-changelog-spec.md`。若无「变更记录」小节，则先在附录末尾（或简单模板的 ## 5）新增该小节及表头，再追加一行。建议同时将 task 头部 `版本` 递增。

## 注意事项

审查深度应与 task 定位匹配；按复杂度裁剪检查项；输出遵循 workflow-output-principles；实现细节属于下游阶段。
