# Task 变更记录规范

## 概述

当 **vet 环节用户反馈** 导致对 task 文档的实质性修改时，执行修改的 Agent 须在 task 文档的「变更记录」小节追加一条结构化记录，完整反映任务产出过程。本文档为变更记录的 SSoT（格式、位置、触发、版本约定）。

## 触发条件

同时满足以下全部时，应追加一条变更记录：

1. **上下文**：本会话内有过 vet 输出（或用户明确引用本次 vet 的结论）。
2. **用户意图**：用户表达要按 vet 结果修改 task（如「按建议改」「采纳 D2」「把 F2 的验收标准改成…」或选择「调整 task」后给出具体修改内容）。
3. **实际发生**：对 `.cursor/.lingxi/tasks/<taskId>.task.<标题>.md` 做了实质性修改（正文、表、章节、F 条等）。

仅讨论或仅输出修改建议而未改 task 文件时，不写变更记录。

## 存放位置

- **若 task 已有「附录」**：在附录末尾新增小节 **「变更记录」**，编号顺延（如已有 11.1、11.2 则为 11.3；已有 8.1–8.3 则为 8.4）。
- **若 task 无附录**（如简单模板）：新增 **「## 5. 变更记录」**（或按现有最后一节编号顺延）。

若无「变更记录」小节，则先创建该小节及表头，再追加一行。

## 单条记录结构

每条记录对应表格中的一行，字段如下：

| 字段 | 必填 | 说明 |
|------|------|------|
| 日期 | 是 | ISO 8601 日期或日期时间（如 `2025-03-08` 或 `2025-03-08T14:00:00Z`）。 |
| 来源 | 是 | 固定 `vet`（预留 plan / review / 用户直接修改）。 |
| 触发 | 是 | 用户反馈的一句话摘要（如「采纳 D2 改进建议」「按 Blockers 修改 F1、F2 验收标准」）。 |
| 变更摘要 | 是 | 章节/编号 + 变更类型（修改 / 新增 / 删除）+ 简要说明；多条用分号分隔。 |
| 关联维度/问题 | 否 | 若可对应本次 vet 的维度或问题，可填如 D2、Blockers#1、High#2。 |

## 表格格式

- 表头一行：`| 日期 | 来源 | 触发 | 变更摘要 | 关联维度/问题 |`
- 新记录插入在**表头下方**，**倒序**（最新在上）。

## 版本

建议（非强制）在追加变更记录时，将 task 头部元数据中的 `版本` 递增（如 1.0 → 1.1），表示经过一轮 vet 反馈修订。

## 示例

```markdown
### 11.3 变更记录

由 vet 反馈导致 task 修改时在此追加，格式见本 skill 的 `references/task-changelog-spec.md`。

| 日期       | 来源 | 触发                     | 变更摘要                                      | 关联维度/问题 |
| ---------- | ---- | ------------------------ | --------------------------------------------- | ------------- |
| 2025-03-08 | vet  | 采纳 D2 改进建议         | F1、F2：修改（验收标准改为可二值判定）        | D2            |
| 2025-03-08 | vet  | 按 Blockers 修改验收标准 | §4 功能需求表 F3：修改（补充边界/异常 1 条）   | Blockers#1    |
```

## 参考

- vet skill：当用户反馈导致 task 修改时，约定执行修改的 Agent 追加本条记录。
- task skill：当补充/修改 task 且修改来源于 vet 反馈时，须在「变更记录」中追加一条并引用本 spec。
