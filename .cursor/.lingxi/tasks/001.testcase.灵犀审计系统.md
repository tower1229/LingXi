## 2. 集成/手工测试用例

### TC-001: 主审计 — 单次 Hook 触发后 audit 有一行 NDJSON

**前置条件**：

- T1、T2 已完成；audit 文件路径为 `.cursor/.lingxi/workspace/audit.log`（或 req 约定路径）
- 可触发至少一种 Hook（如 beforeSubmitPrompt：用户提交一条消息）

**测试步骤**：

1. 清空或备份现有 audit.log（可选）
2. 在 Cursor 中提交一条用户消息，触发 agent 循环
3. 打开 `.cursor/.lingxi/workspace/audit.log`，查看新增行

**预期结果**：

- 文件中出现至少一行 NDJSON
- 该行可被 `JSON.parse` 解析；包含 `ts`、`event`、`conversation_id`（或占位）
- 主流程未中断（对话正常进行）

**边界条件**：

- 首次运行：workspace 目录不存在时，脚本应先创建目录再写入（或由安装脚本预先创建）

---

### TC-002: 主审计 — 9 类事件均有对应 event 写入

**前置条件**：

- T1、T2 已完成；能触发到 9 类事件（beforeSubmitPrompt、afterAgentResponse、preToolUse、postToolUse、postToolUseFailure、subagentStart、subagentStop、sessionEnd、stop）

**测试步骤**：

1. 通过正常使用（发消息、用工具、启停子代理、结束会话等）尽量覆盖 9 类事件
2. 检查 audit.log 中出现的 `event` 取值

**预期结果**：

- 与 req §8.2 主审计 event 一致：`before_submit_prompt`、`after_agent_response`、`pre_tool_use`、`post_tool_use`、`post_tool_use_failure`、`subagent_start`、`subagent_stop`、`session_end`、`stop`
- 每类事件特有字段符合约定（如 pre_tool_use 含 tool_name、tool_use_id，post_tool_use 含 duration_ms）

---

### TC-003: 主审计 — Hook 返回放行 JSON

**前置条件**：

- T1 完成；Hook 配置指向 lingxi-audit.mjs

**测试步骤**：

1. 触发任意已注册 Hook
2. 观察主流程是否被拦截（对话/工具调用是否正常继续）

**预期结果**：

- 主流程不中断；Cursor 收到脚本 stdout 的合法放行 JSON（如 continue: true / decision: "allow"）

---

### TC-004: hooks.json 配置正确

**前置条件**：

- T2 已完成

**测试步骤**：

1. 打开 `.cursor/hooks.json`
2. 检查 hooks 下是否存在：beforeSubmitPrompt、afterAgentResponse、preToolUse、postToolUse、postToolUseFailure、subagentStart、subagentStop、sessionEnd、stop
3. 检查每个 command 指向项目内 `lingxi-audit.mjs` 的路径是否正确

**预期结果**：

- 9 个 key 均存在；command 路径可解析（如 `node .cursor/hooks/lingxi-audit.mjs`）

---

### TC-010: 工具链路闭环 — pre/post 通过 tool_use_id 可关联

**前置条件**：

- T1、T2 已完成；`preToolUse`、`postToolUse`、`postToolUseFailure` 已注册

**测试步骤**：

1. 在一次会话中触发至少一次成功工具调用与一次失败工具调用
2. 打开 audit.log，定位 `event=pre_tool_use` 的若干行，记录 `tool_use_id`
3. 校验同 `tool_use_id` 是否存在 `post_tool_use` 或 `post_tool_use_failure`

**预期结果**：

- `pre_tool_use` 行包含 `tool_name`、`tool_use_id`、`conversation_id`、`generation_id`
- 对同一 `tool_use_id`，后续存在且仅存在一种结果事件：`post_tool_use` 或 `post_tool_use_failure`
- 可按 `tool_use_id` 还原工具调用链路（pre -> post）

### TC-005: sessionStart 约定包含会话 ID 与 lingxi-memory 传入要求

**前置条件**：

- T3 已完成

**测试步骤**：

1. 打开 `.cursor/hooks/session-init.mjs`
2. 查看 ADDITIONAL_CONTEXT（或等价输出）是否包含：当前会话 ID 的说明、以及「调用 lingxi-memory 时请在 input 中传入 conversation_id（及可选 generation_id）」的表述
3. 若启用了心跳：当 trigger_heartbeat 为 true 时，约定中应包含调用 lingxi-session-distill、传入 candidate_ids 与 enqueued_by，且说明子代理内部会写 heartbeat.triggered。

**预期结果**：

- 约定文本中明确包含上述内容；新会话开始时该约定被注入

### TC-006: 记忆审计 — 写 note 后 audit 出现 memory*note*\* 行

**前置条件**：

- T1、T4 已完成；主 Agent 调用 lingxi-memory 时传入 conversation_id（及可选 generation_id）
- 能触发一次记忆写入（如 /remember、工作流品味嗅探或心跳会话提炼等写入）

**测试步骤**：

1. 触发一次记忆创建或更新（如执行 /remember 并完成门控写入）
2. 检查 audit.log 最新行

**预期结果**：

- 出现 `event` 为 `memory_note_created` 或 `memory_note_updated` 的 NDJSON 行
- 该行含 `ts`、`event`、`conversation_id`（在主 Agent 传入时非空）、`note_id`、`operation`、`source`、`file` 等（符合 req §8.2 记忆审计约定）

---

### TC-007: 记忆审计 — conversation_id 会话级关联

**前置条件**：

- 同一会话内既有主审计事件又有记忆审计事件

**测试步骤**：

1. 在同一会话中：提交消息（主审计）、触发记忆写入（记忆审计）
2. 用同一 conversation_id 过滤 audit.log

**预期结果**：

- 过滤结果包含该会话的主审计行与记忆审计行；按 ts 可排序得到完整时间线

---

### TC-008: INDEX 与 note Meta 含 CreatedAt、UpdatedAt、Source、Session

**前置条件**：

- T5、T4 已完成；已有一条新写或更新的记忆

**测试步骤**：

1. 新建或更新一条记忆并完成写入
2. 打开 `.cursor/.lingxi/memory/INDEX.md`，查看对应行
3. 打开对应 note 文件，查看 Meta 区

**预期结果**：

- INDEX 表头含 CreatedAt、UpdatedAt、Source、Session（或等价列名）；对应行有合理取值
- note 内 Meta 含上述字段（或 CreatedInSession/UpdatedInSession）；写入/更新后内容正确

### TC-009: 审计脚本异常时主流程放行

**前置条件**：

- T1 完成；可模拟脚本异常（如 audit 路径无写权限、或临时修改脚本在首行 throw）

**测试步骤**：

1. 人为使审计脚本抛出异常（如去掉写权限或脚本内 throw）
2. 触发任意已注册 Hook
3. 观察主流程是否被阻塞

**预期结果**：

- 脚本 catch 后向 stdout 输出放行 JSON（continue: true / decision: "allow"）；主流程不被拦截

---

### TC-011: 记忆提取审计 v2 与完整性软强制

**前置条件**：

- 已启用 v2 审计事件：`memory.retrieve.performed` / `memory.retrieve.skipped` / `memory.retrieve.missing` / `memory.retrieve.invalid`

**测试步骤**：

1. 触发一轮正常用户输入并执行 memory-retrieve
2. 检查 audit.log 是否出现 `memory.retrieve.performed`（或显式跳过时出现 `memory.retrieve.skipped`）
3. 抽查 `memory.retrieve.performed` 字段完整性：`query`、`hits`、`adopted`、`rejected`、`semantic_called`、`keyword_called`、`candidate_read_count`、`decision`
4. 在不产生 retrieve 事件的轮次（或模拟缺失）检查是否自动出现 `memory.retrieve.missing`

**预期结果**：

- 每轮有且仅有一次 retrieve 结果事件（performed 或 skipped）；缺失时有 missing
- `missing` 为告警事件，不阻断主流程

---

### TC-012: 心跳相关事件与 heartbeat-control.json（可选）

**前置条件**：

- 已启用会话提炼心跳（session-init 调用 heartbeat-check.mjs）；audit 中存在至少一个已 session_end 且未在 processed_conversation_ids 中的会话；距上次 last_distillation_completed_at 超过 30 分钟。

**测试步骤**：

1. 开启新会话，触发 sessionStart
2. 检查 additional_context 是否在满足条件时包含「调用 lingxi-session-distill」、candidate_ids 与 enqueued_by
3. 检查 `.cursor/.lingxi/workspace/heartbeat-control.json` 是否在触发时写入 pending_distillation、heartbeat.running=true
4. 子代理启动后检查 audit 是否出现 `heartbeat.triggered`（由 lingxi-session-distill 写入，ts、conversation_id、candidate_ids、reason）
5. 子代理完成后检查是否出现 `heartbeat.distillation_completed` 或 `heartbeat.distillation_failed`；heartbeat-control.json 中 pending_distillation 已清空、last_distillation_completed_at 已更新、heartbeat.running=false

**预期结果**：

- 心跳触发与收尾逻辑符合 001.task 中「心跳相关事件」约定；控制文件状态正确

**脚本单元测试**：`runHeartbeatCheck` 逻辑由 `test/hooks/heartbeat-check.test.mjs` 覆盖（30 分钟/锁/候选排除/最多 3 条等）；运行 `yarn lx:test:hooks` 可执行。

## 3. 验收检查清单（与 req §7 对应）

- [ ] 主审计：9 类 Hook 事件均能触发并写入 audit.log，且返回正确放行/决策 JSON。
- [ ] 记忆审计：子代理创建/更新/删除 note 及更新 INDEX 后，audit 中出现对应 memory\_\* 行，且含 conversation_id（在主 Agent 传入时）。
- [ ] sessionStart 约定中包含会话 ID 与「调用 lingxi-memory 时传入 conversation_id」的说明。
- [ ] INDEX 与 note Meta 含 CreatedAt、UpdatedAt、Source、Session（或等价字段）；写入/更新后内容正确。
- [ ] 按 conversation_id 过滤 audit 文件可得到该会话的主事件与记忆事件，并按 ts 可排序。
- [ ] 审计脚本异常时主流程不被拦截（返回放行 JSON）。
- [ ] 记忆提取审计采用 v2 事件；每轮可观测到 performed/skipped 或 missing（软强制）。
- [ ] 心跳：当 sessionStart 触发心跳时，lingxi-session-distill 子代理在启动时写入 `heartbeat.triggered`；子代理完成后可写入 `heartbeat.distillation_completed` 或 `heartbeat.distillation_failed`；`heartbeat-control.json` 在入队后含 pending_distillation 与锁，完成后含 last_distillation_completed_at 与已合并的 processed_conversation_ids。
